현재 코드베이스와 Canvas·HarnessSpec 동기화 구조를 먼저 조사하고, 현재 열려 있는 https://cloud.dify.ai/ 와 https://base-ui.com 을 분석한 뒤 Harnest의 UI/UX와 제품 구조를 실제로 개편하라. 계획이나 보고서에서 멈추지 말고 구현·검증까지 완료한다.

이 작업의 목적은 아래 항목을 기계적으로 모두 구현하는 것이 아니다. 요구사항과 기능 예시는 현재 가설이므로, 조사 결과 더 나은 구조가 있다면 수정·통합·제거하거나 새로운 대안을 선택해도 된다. 기존 PRD와 코드 구조 역시 비판적으로 검토하되 HarnessSpec, Core, CLI, SDK 등 정상 동작 중인 핵심 기능과 데이터 호환성은 보존한다.

## 1. Canvas 노드 추가 UX 개편

* 좌측 컴포넌트 사이드바와 Drag & Drop 의존성을 최소화한다.
* 각 노드의 연결 가능한 위치에 Hover `+`를 표시한다.
* 클릭 시 해당 위치에 연결 가능한 노드만 검색·선택할 수 있는 MoreMenu를 연다.
* 선택 즉시 적절한 노드와 Edge를 생성한다.
* 연결 불가능한 항목, 키보드 조작, Undo·Redo와 오류 상태를 명확히 처리한다.

## 2. Dify 기반 UX 전면 재설계

Dify의 화면 구성, Canvas 조작, Inspector, 설정 계층, 실행·테스트·로그·오류 UX를 폭넓게 조사하고 Harnest에 적합한 부분만 재해석한다.

* 핵심 설정만 우선 노출하고 고급 설정은 Accordion, Drawer, Modal 등으로 분리한다.
* 불필요한 내부 정보와 중복 설명은 기본 화면에서 숨긴다.
* 사용자의 현재 상태와 다음 행동이 즉시 이해되어야 한다.
* Harnest의 Harness 설계·실험·검증 흐름에 맞게 구성한다.

## 3. 디자인 시스템 구축 및 전체 통합

Base UI를 기반으로 공통 컴포넌트와 Design Token을 구축하고 Canvas, Inspector, Header, Sidebar, Test, Trace, Playground, Settings 전반에 적용한다.

* 현대적이고 절제된 시각 디자인
* 일관된 간격, 계층, 상태, 메뉴와 피드백
* Light·Dark Theme, 반응형, 접근성
* 자연스러운 애니메이션
* 기존 중복 UI와 일관성 없는 스타일 정리 (dify와 유사하게 현대적이고 깔끔한 UI/UX라면 매우 환영함.)

Base UI의 컴포넌트를 제품 사용성에 필요한 구성만 선택한다.

## 4. Dify 기능 조사 및 선별 도입

Dify와 관련 Agent Builder 제품을 조사하여 Harnest에 실질적으로 유용한 기능을 선별 구현한다.

기능 목록을 미리 고정하지 말고 노드 추가, 템플릿, 자동 설정, Validation, 실행·Trace, Provider 관리, Import·Export, 오류 복구 등 전체 개발 흐름에서 사용자의 작업을 줄이는 기능을 우선한다. 단순한 외형 복제나 일반 Workflow 자동화 기능 추가는 피한다.

## 5. Harnest만의 명확한 차별 기능 구현

Harnest를 **사용자가 원하는 AI Agent Harness를 설계·검증하고 SDK·CLI·API·MCP를 통해 자기 서비스에 통합하는 “하네스계의 Supabase”**로 발전시킨다.

차별 기능을 먼저 정하고 근거를 끼워 맞추지 말라. Dify, n8n, Agent Builder, Harness Engineering 도구와 현재 코드베이스를 조사한 뒤 서로 다른 제품 방향을 비교하고 가장 강력한 방향을 선택해 실제로 구현한다.

HarnessSpec, 테스트·평가, Trace 비교, 정적 분석, 권한·실패 정책, SDK 통합, 독립 실행 등은 후보일 뿐 고정 답안이 아니다. 더 강력한 방향을 발견하면 기존 가설을 변경해도 된다. 단, 선택한 차별점은 소개 문구가 아니라 Studio와 Core·CLI·SDK 등 실제 동작으로 이어져야 한다.

## 6. 구현 원칙

* 기존 코드, 상태 흐름, 데이터 구조와 프로젝트 규칙을 먼저 파악한다.
* 필요하면 기존 UX와 구조를 과감히 리팩터링하되 핵심 기능과 저장 데이터는 손상시키지 않는다.
* Mock이나 Placeholder가 아닌 실제 기능으로 구현한다.
* Canvas와 HarnessSpec의 양방향 동기화 및 Import·Export를 유지한다.
* 로딩, 빈 상태, 오류, Timeout, 연결 실패, 복구 상태를 처리한다.
* Secret을 Spec, 로그, Trace 또는 클라이언트에 노출하지 않는다.
* Dify와 Base UI는 참고 자료로만 사용하고 코드·브랜드를 그대로 복제하지 않는다.
* Build, Type Check, Lint와 관련 테스트를 실행하고 발견된 오류의 원인을 해결한다.
